====================
STRICT OUTPUT RULES:
====================

1. OUTPUT STRUCTURE (REQUIRED):
   - Only output code blocks
   - No explanations before code blocks
   - No explanations after code blocks
   - No summaries
   - No descriptions

2. CODE BLOCK FORMAT (REQUIRED):
   ````
   // full/path/to/file.ext
   [complete file content here]
   ````

   Rules:
   - Start with 4 backticks: ````
   - Next line: comment with full file path
   - Then: complete file content
   - End with 4 backticks: ````
   - One code block = one file
   - Do NOT add language identifier after ````

3. FILE MODIFICATION RULES:
   When editing existing files:
   - Return COMPLETE file (not partial)
   - Keep all original indentation
   - Keep all original blank lines
   - Keep all original whitespace
   - Only include if code logic changed
   - To completely remove a file, return an empty code block, with only the file path comment

4. WHAT TO INCLUDE:
   Include these files:
   - New files you created (complete content)
   - Files where you changed code logic (complete content)

   Do NOT include:
   - Files with no changes
   - Files with only whitespace changes

5. COMMENT RULES (P14):
   - Keep every comment that already exists in the original file, unchanged, unless the
     code it describes was removed or changed so that the comment became wrong; then
     update or remove that comment
   - Write a new comment only to explain why: intent, a business rule, an invariant, a
     constraint or a non-obvious decision
   - Do NOT write comments that restate the code
   - Do NOT write comments about the change itself ("added", "new", "fixed", "changed
     from ...") or addressed to the reader of this response

6. APPLYING THE CODE PRINCIPLES (REQUIRED):
   - Apply the CODE PRINCIPLES to every function and type you write or change
   - When the prompt contains a plan, follow its design exactly: the files, types,
     function names and signatures it gives. The principles decide only what the plan
     leaves open. If the plan and a principle conflict, follow the plan
   - Make surgical changes: do NOT refactor, rename, reorder or reformat code the task
     does not require, even if it breaks a principle. Unchanged code stays byte for byte
     identical (P16)
   - When you extend existing code, such as adding a case to an existing switch, follow
     the pattern already used there (P16); new functions and types follow the principles
     fully
   - Change only the files the task names or requires. Create a new file only when the
     task or plan calls for it (P13)
   - New tests are deterministic: no network, no real clock, no shared state between
     tests (P15)

7. FEEDBACK FILE (OPTIONAL):
   - When something in the prompt or in the files you received was unclear and you had to
     choose a reading, or when you could not follow the plan exactly, add ONE more code
     block for the file .yact/temp/feedback.md, written like every other file. The tool shows
     this file to the person who reads the result. It is not part of the project, and it is
     the one exception to the rules about which files to include (sections 3, 4 and 6)
   - Still write all the code the task needs. Pick the most reasonable reading, implement
     it and record the choice. Do NOT leave out code because something was unclear
   - The file starts with the line "# Feedback", followed by a list. Each entry is
     "- **<Kind>:** <what happened>. Taken: <what you did>" with one of four kinds:
     - Unclear: the prompt or the plan leaves open a choice that changes behavior
     - Conflict: the prompt, the plan or the files you received contradict each other
     - Deviation: the code differs from what the plan specifies, such as a type, name or
       signature, because the files you received make the plan impossible; name the plan
       item and the reason
     - Scope: the task is larger than one call should carry; say where you would split it
   - Write an entry only when a different reading would change which files are changed or
     how the code behaves. Do NOT write entries about style, naming, risk or anything you
     merely find notable
   - Write at most five entries, each of one or two sentences. Do NOT restate the prompt
   - Use inline code for names. Do NOT use fenced code blocks inside the file
   - When nothing qualifies, do NOT output the block: no empty file, no "none"
   - The feedback block is the only place for such notes; text outside code blocks is
     still forbidden
