Lint the prompt.
Review the change against its plan.

YACT is a command-line tool for AI-assisted coding with a method built in. You write a prompt. The model turns it into a plan and lists what your prompt left open. Each step is then written by one call, and the plan stays with the change, so a reviewer can see what was asked.

@@ 01 · The problem @@

AI writes the code faster. The cost shows up later.

Coding tools take a short prompt, decide the rest themselves and hand back a change. That is fast. It also means:

The model does more than you asked

Nobody wrote down what the change should touch, so the model decided.

Gaps get filled in silently

Where the prompt was vague, the model picked an answer and moved on. You find out in review.

Review gets expensive

A pull or merge request arrives as a diff without the intent behind it. The reviewer has to work out what was asked, what was assumed and what the model looked at.

Developers drift from their code

When a tool explores and decides for you, you slowly lose your picture of the codebase.

Juniors miss the learning

Juniors learn from seniors, and review is where much of that happens. A pull request nobody can review properly teaches nothing.

A better model does not fix this. The prompt was never checked, and the intent was never written down.

@@ 02 · The principle @@

A prompt is a program in a very high-level language.

So it can be linted like one. When you run y plan, the model checks your prompt for two properties and writes what it finds into the plan, before any code exists. YACT does not run your code or prove it right.

1

Complete

Every reference in the prompt should resolve to something the model can see. When one does not, the plan gets a ## Missing context section. That is an error, and it blocks act.

2

No silent assumptions

Where the prompt left a choice open, the model writes its choice down under ## Assumptions. That is a warning, and it never blocks act. If an assumption is what you want, it is fine and can stay in the plan. If it is not, correct the prompt and plan again.

A plan is ready when Missing context is gone and you have read the assumptions and they are true.

A linter, not a proof. The model makes these checks and it can miss an entry, so a plan without an Assumptions section is not proof that nothing was open. You still read the plan and check the change.

Read The YACT way

y plan, after linking the missing file # Goal ## Steps ### [ ] 1. Add email validation ## Assumptions - Invalid addresses return an error. (no ## Missing context) Ready: y -s next act
@@ 03 · The plan @@

The plan binds the change to its intent and its context.

A plan is a Markdown file that you read and edit before any code exists. It records four things in one place.

01

The intent

The goal in your words, then the steps that reach it.

02

The change

Each step names the file it changes.

03

The context

Each step links the files the model is given to write it.

04

The assumptions

What the model chose where your prompt left something open.

This is what helps a reviewer. With the plan beside the pull request, they review the change against what was asked.

Commit the plan or copy it into the pull request: how it reaches the reviewer is for your team to decide.

@@ 04 · How it works @@

From prompt to pull request in five steps.

  1. Write the prompt and link the files

    y new starts a fresh prompt. y read links files by path or glob, y keyword Signup links every file that contains a word, and ((Signup)) in your prompt does the same at call time. The linked files are the context.

  2. Plan, then read the two sections

    y plan turns the prompt into a plan, one file per step. Link what ## Missing context asks for, check the ## Assumptions, and plan again if you changed anything.

  3. Implement one step

    y -s next act writes the complete file for the next unticked step and ticks it off. If it finds a problem in the plan, it says so in a feedback note that YACT prints.

  4. Check the change

    Read git diff against the step, then run the next one.

  5. Open the pull request

    The plan goes with it, so the reviewer has the intent, the files and the assumptions.

terminal $ y new $ y read "internal/signup/*.go" $ y plan "validate email addresses on signup" $ y -s next act $ git diff
yact-prompt.md, after step 1 # Goal Validate email addresses on signup. ## Steps ### [x] 1. Add email validation **File:** internal/signup/validate.go **Context:** internal/signup/signup.go ### [ ] 2. Cover it with tests **File:** internal/signup/validate_test.go **Context:** internal/signup/validate.go

By default, plan and act also send an index: the names of the files, classes and functions in your project, with no code. It helps the model find its way, and -i none turns it off.

Every command prints the model, the token counts and the estimated cost. Add --dry-run --verbose to see exactly what would be sent, without calling the API.

@@ 05 · Context by keyword @@

Do not know the file? Name the thing.

Paths work when you know where the code lives. For a rename, or a change to something used in many places, name it and YACT finds every file that mentions it.

y keyword PlanStep

Searches once and links every matching file in yact-prompt.md. A snapshot you can read and trim.

((PlanStep))

Write it in your prompt. The search runs at call time, so new files are included, and the marker is removed before the model sees the text.

Whole words, any style

plan step finds PlanStep and plan_step. Add file types with y config ext vue. Check the result with --dry-run --verbose.

A trivial change does not need a plan. For something like a rename, give the prompt straight to act. Keywords work there too:

y act "Rename PlanStep to Step and update every use. ((PlanStep))"

A keyword links files by what they contain, and you can see the list before anything is sent.

@@ 06 · Compared @@

Not a smaller agent. A tool with a method.

Agents and IDE assistants work whichever way you ask them to. YACT has one way of working, and it is built in.

YACTCoding agentIDE assistant
MethodBuilt in: lint the prompt, plan, then actNone prescribedNone prescribed
Who sets the contextYou link files; the plan lists what else is neededThe agent, by exploringYou, by selecting code
Gaps in the promptListed before any code is writtenFilled in along the wayFilled in along the way
Model callsOne per commandMany, in a loopMany, interactive
Runs tests and retriesNoYesLimited
What the reviewer getsThe change and its planA diffA diff
CostShown for every callVaries with the runUsually a subscription
Best forPlanned changesOpen-ended and exploratory workEveryday typing

If you want a tool that finds the files, runs the tests and fixes the failures, use an agent. If you want every change to start from a linted prompt and arrive with its plan, use YACT. Many people will use both.

@@ 07 · Who it is for @@

For developers, and for the people who review their work.

Developers who know their code

You want the model to type while you stay in charge of what changes. Writing the prompt and reading the plan keep you up to date with your code.

Team leads

You choose how your team works with AI. With YACT, an AI-assisted pull request comes with the plan it was made from.

Teams where review is the bottleneck

Reviewing a change against its plan is cheaper than working out the intent from a diff, and the assumptions are already listed.

Seniors who mentor juniors

Juniors learn from seniors. A junior's pull request that comes with its plan can be reviewed properly, and that review is where the junior learns.

@@ 08 · Trade-offs @@

What the method costs you.

Each of these is a deliberate trade. Here they are plainly.

−You link the files. Nothing explores for you, so you need to know your code. Keywords help, and the plan tells you what is still missing.
−You read the plan. Missing context has to be fixed and assumptions have to be checked. That is work, and it is the work that would otherwise surface in review.
−Whole files, kept small. Keep files to a few hundred lines so a complete file fits the output limit. YACT warns above 300 lines.
−You run the tests. YACT never runs or retries anything by itself. If a test fails, that is your next prompt.
−Anthropic models only, for now.
+A good fit. You know your codebase, and you want every change to start from a plan you have read.
−Not a fit. You want a tool that finds the files, runs the tests and fixes the failures on its own.
@@ 09 · Make it yours @@

Every command is a text file.

Six commands ship with YACT, each a plain-text system prompt in ~/.yact/systemprompts/. Add a file and you have a new command, with no rebuild. Even the lint rules are in those files, so you can read them and change them.

plan
Turns a prompt into steps, one file per step, and lists what is missing and what it assumed
act
Writes complete files and nothing else
ask
Answers questions and changes nothing
review
Reviews a diff against its prompt
analyze
Checks code against published principles
bash
Prints shell commands for you to read and run
~/.yact/systemprompts/ask.txt, the first lines flags: --model sonnet --output print CODEBASE QUESTION ANSWERING ASSISTANT You are a codebase expert assistant. Your job is to: - Answer questions about how the codebase works - Explain code functionality and architecture $ y ask "how does keyword search pick files?"
@@ 10 · Questions @@

Questions people ask first.

What if the plan lists assumptions?

Read them. Each one is a choice the model made because the prompt left it open. If it is what you want, leave it in the plan. If it is not, say what you want in the prompt and run y plan again. Assumptions never block act.

Does the lint prove the code is right?

No. The model makes the lint during the plan call, and it shows what the model noticed was missing or open. It can miss an entry, so you still read the plan and check the change. What it does is put the decisions in front of you before the code exists, where they are cheap.

Does it send my whole repository?

No. It sends the files linked in the prompt or the plan, the prompt itself, and .yact/domain.txt and captured output if you use them. By default, plan and act add an index of file, class and function names, with no code. Turn it off with -i none.

Do I always need a plan?

No. For a trivial change, such as a rename, give the prompt straight to act. For anything a reviewer will want to understand, plan first.

Which models can I use?

Claude Haiku by default, and Sonnet, Opus and Fable with -m, depending on your Anthropic account. Set a default with y config claude_model.

What does it cost?

You pay Anthropic directly. YACT prints the token counts and the estimated cost after every call.

Where do my API key and code go?

The key is stored in ~/.yact/config and sent only to Anthropic. There is no telemetry. The only network calls are the API calls you trigger and downloads of system prompts from the project's GitHub repository.

Can it write outside my project?

No. Absolute paths and paths that leave the project directory are rejected. Inside the project, the model can write any file, not only the linked ones, so check the change before you commit.

How is it different from aider, Claude Code or Cursor?

Those tools are method-agnostic: they work in a session and do what you ask, whichever way you work. YACT has a method built in. The prompt is linted, you read the plan before any code exists, and the change comes with its plan.

Is it made by Anthropic?

No. It is an independent open-source project under the GNU GPL v3.
