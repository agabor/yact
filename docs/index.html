@@ 01 · The problem @@

AI took the friction out of coding. Some of it was doing a job.

Agentic tools explore your repository, decide what to change, run commands and keep going until they think they are done. That is fast. It also means:

Changes are bigger than the task needed

Nobody chose the scope, so the model did.

Gaps get filled in silently

Where the prompt was vague, the model picked an answer and moved on. You find out in review.

Developers drift from their code

When you stop editing, you slowly lose your picture of it.

Juniors skip the learning

Finding the right place and making a small change is how people come to understand a codebase.

Friction was never only a cost. Some of it was where understanding and judgment happened.

@@ 02 · The principle @@

A prompt is a program in a very high-level language.

Then it can be checked like one. YACT is the linter. It does not run your code or prove it right. It checks the prompt for two properties, and it shows you the result before any code is written.

1

Complete

Every reference in the prompt resolves to something the model can see. When one does not, the plan gets a ## Missing context section. That is an error, and it blocks the run.

2

No silent assumptions

Every choice the model made where the prompt was open is written down under ## Assumptions. When there are none, the section is simply absent. That is a warning. It never blocks, because the decision is yours.

Settle an entry by sharpening the prompt or linking the file, then plan again. The prompt is ready when both lists are empty.

A linter, not a proof. The lists show what the model noticed. It can miss an entry, as any checker can, so you still read the plan and the diff.

@@ 03 · The idea @@

YACT keeps the friction where it belongs.

The model does the typing. You make the decisions.

01

You choose the context

You link the files that matter, by path or by keyword, and only those are sent. You have to know your code, and you stay in it.

02

Plan first, then one file at a time

The plan is a Markdown file you read and edit before any code exists. Each step changes exactly one file.

03

One call, a diff you can read

Every command makes a single API call and writes complete files. No loop, no hidden exploration. You check the result with git diff.

@@ 04 · How it works @@

From task to diff in four steps.

  1. Write the prompt and pick the files

    y new starts a task. y read links files by path or glob, y keyword Signup links every file that contains a word, and ((Signup)) in your prompt does the same at call time. Only linked files are sent.

  2. Plan, then settle the lists

    y plan writes a Markdown plan, one file per step, and lists what is missing and what it assumed. Read it, edit it, plan again until both lists are empty.

  3. Implement one step

    y -s next act writes the complete file for the next unticked step and ticks it off. If it hit a problem in the plan, it says so in a feedback note that YACT prints.

  4. Review

    Read git diff, then run the next step.

terminal $ y new $ y read "internal/signup/*.go" $ y plan "validate email addresses on signup" $ y -s next act $ git diff
yact-prompt.md, after step 1 # Goal Validate email addresses on signup. ## Steps ### [x] 1. Add email validation **File:** internal/signup/validate.go ### [ ] 2. Cover it with tests **File:** internal/signup/validate_test.go

Every command prints the model, the token counts and the estimated cost. Add --dry-run --verbose to see exactly what would be sent, without calling the API.

@@ 05 · Context by keyword @@

Do not know the file? Name the thing.

Paths work when you know where the code lives. For a rename, or a change to something used in many places, name it and YACT finds every file that mentions it.

y keyword PlanStep

Searches once and links every matching file in yact-prompt.md. A snapshot you can read and trim.

((PlanStep))

Write it in your prompt. The search runs at call time, so new files are included, and the marker is removed before the model sees the text.

Whole words, any style

plan step finds PlanStep and plan_step. Add file types with y config ext vue. Check the result with --dry-run --verbose.

y act "Rename PlanStep to Step and update every use. ((PlanStep))"

You still decide what is relevant: a keyword picks files by what they contain, and you can see the list before anything is sent.

@@ 06 · Compared @@

Not a smaller agent. A different question.

Who is in control of the change?

Who chooses the filesYou, by path or keywordThe agent, by exploringYou, by selecting code
Gaps in the promptListed before any code is writtenFilled in along the wayFilled in along the way
Model calls per taskOne per commandMany, in a loopMany, interactive
Runs tests and retriesNoYesLimited
What you reviewA plan, then a small diffOften a large diffInline suggestions
CostShown for every callVaries with the runUsually a subscription
Best forPlanned, scoped changes and automationOpen-ended and exploratory workEveryday typing

If you want a tool that finds the files, runs the tests and fixes the failures, use an agent. If you want to decide what changes and read every line that does, use YACT. Many people will use both.

@@ 07 · Who it is for @@

Built for the people who carry the review.

Maintainers

Want AI help without growing the review queue. Every change starts from a plan you can read and ends in a small, reviewable diff.

Teams where review is the bottleneck

Reviewing intent in a short plan is cheaper than reviewing a large diff after the fact, and the assumptions are already listed.

Leads who onboard juniors

The junior links the files and states the intent, a senior reviews the plan, and the junior reads a small change. They use AI and still learn the codebase.

Developers who know their code

You keep files small and want the model to type while you decide.

@@ 08 · Trade-offs @@

What control costs you.

Each of these is a deliberate trade for a smaller diff. Here they are plainly.

−You choose the files. Nothing explores for you, so you need to know your code. Keywords help.
−You settle the lists. A plan with open entries is not ready. That is work, and it is the work that would otherwise surface in review.
−Whole files, kept small. Keep files to a few hundred lines so a complete file fits the output limit. YACT warns above 300 lines.
−You run the tests. YACT never retries by itself, so run them yourself, or in CI, and use a fix step if something fails.
−Anthropic models only, for now.
+A good fit. You know your codebase, you keep files small, and you want to read what changes.
−Not a fit. You want a tool that finds the files, runs the tests and fixes the failures on its own.
@@ 09 · Automation @@

From issue to pull request, by label.

Add a label in GitHub and a workflow runs YACT for you. The pull request description is the plan, so reviewers see the assumptions too. If the plan still has missing context after one retry, the run stops instead of guessing. The label is removed when the run ends, so adding it again retries.

LabelAdd it toYou get
implementAn issueA plan, the code and a new pull request with the plan as its description
updateA pull requestThe plan updated from the latest comment, and new commits on the branch
fixA pull requestCommits that fix a failing build, failing tests or go vet findings
reviewA pull requestA review posted as a comment

Add haiku, sonnet or opus to choose the model. Without one, Haiku runs implement, update and fix, and Sonnet runs review.

@@ 10 · Make it yours @@

Every command is a text file.

Six commands ship with YACT, each a plain-text system prompt in ~/.yact/systemprompts/. Add a file and you have a new command, with no rebuild. Even the lint rules are in those files, so you can read them and change them.

plan
Splits a task into steps, one file per step, and lists what is missing and assumed
act
Writes complete files and nothing else
ask
Answers questions and changes nothing
review
Reviews a diff against its task
analyze
Checks code against published principles
bash
Prints shell commands for you to read and run
~/.yact/systemprompts/ask.txt, the first lines flags: --model sonnet --output print CODEBASE QUESTION ANSWERING ASSISTANT You are a codebase expert assistant. Your job is to: - Answer questions about how the codebase works - Explain code functionality and architecture $ y ask "how does keyword search pick files?"
@@ 11 · Questions @@

Questions people ask first.

What if the plan lists assumptions?

Read them. Each one is a choice the model made because the prompt did not. Keep it by stating it in the prompt, or change it, then run y plan again. The run is never blocked by assumptions, but a plan with none is the one you can trust most.

Does the lint prove the code is right?

No. It shows what the model noticed was missing or open. It can miss an entry, so you still read the plan and the diff. It moves the decisions in front of you, where they are cheap.

Does it send my whole repository?

No. Only the files you linked, the message files in .yact/ and your task. With -i, a code index of declaration signatures is added.

Which models can I use?

Claude Haiku by default, and Sonnet, Opus and Fable with -m, depending on your Anthropic account. Set a default with y config claude_model.

What does it cost?

You pay Anthropic directly. YACT prints the token counts and the estimated cost after every call.

Where do my API key and code go?

The key is stored in ~/.yact/config and sent only to Anthropic. There is no telemetry. The only network calls are the API calls you trigger and downloads of system prompts from the project's GitHub repository.

Can it write outside my project?

No. Absolute paths and paths that leave the project directory are rejected.

How is it different from aider, Claude Code or Cursor?

Those tools work in a session and can search, run commands and retry on their own. YACT has no session: one command, one call, and you decide the scope.

Is it made by Anthropic?

No. It is an independent open-source project under the GNU GPL v3.
