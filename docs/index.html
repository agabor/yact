One command. One API call. Your files.

YACT is a small command-line tool. You choose the files, it sends them to the model once and writes complete files back. No agent loop, no surprises.

What it does

Most coding tools decide for you: which files to read, which commands to run, when to stop. YACT does exactly what you ask, once. You pick the context, you read the plan, you review the diff.

Each command makes a single API call. Complete source files in the response are written to disk, and any prose is printed to your terminal.

How it works

  1. Pick the files. y read adds links to a plain Markdown task file, yact-prompt.md. Every project file whose path appears in the task is sent along as context.

    y new
y read "commands/*.go"

  2. Plan, if you want one. The plan is saved as an editable Markdown file. Each step changes one file and lists the files it needs.

    y -p plan "add a --version flag"

  3. Implement. One step, one API call. Complete files are written to your working tree and the step is ticked off in the plan.

    y -s next act

  4. Review. Read the diff the way you would read anyone else's. Then run the next step.

    git diff

Why you might like it

Predictable
Exactly one API call per command. Every call prints the model, the token counts and an estimated cost, and an input-line limit stops you from sending more than you meant to.
Scriptable
There is no session to manage. Each command reads its context, makes one call and exits, so it fits a shell loop, a Makefile target or a CI job.
Transparent
The task is a Markdown file you can read and edit. Every raw response is logged. There is no telemetry and no background process.
Cheap to run
Haiku is the default model. Add -b to submit a batch at a 50% discount, or -n to read a response before y commit writes it.

Who it's for

Whether you are two weeks into your first job or twenty years in, the workflow is the same: you choose the context, you read the plan, you review every change.

For developers

You know your codebase and you want edits you can predict, script and review. You keep source files small, and you would rather compose commands than chat with an agent.

For people learning the job

Working with AI should not mean shipping code you don't understand. YACT's workflow keeps the decisions with you:

  • You choose the files, so you have to find your way around the codebase.
  • Ask for a plan first and read it before any code is written: what changes, in which file, and why.
  • You review one small change at a time, one file per step.
  • You can ask without changing anything. y ask "why does this function return early?" explains code and leaves your source files alone.

YACT does not do the thinking for you.

For mentors and reviewers

Review the intent, not just the diff.

  • Read the plan first. Is the breakdown right? Is each step one file? Is the context sensible? Fixing a plan is cheaper than fixing code.
  • Teach with plans. Share a plan as an example of how you would break a task down, and ask a junior to explain theirs.

Plans make reviews better

A pull request normally shows what changed. A YACT plan also shows what was meant to change, step by step.

# Goal
Add a --version flag that prints the build version.

## Steps
### [x] 1. Add version constant
**File:** config/config.go
**Context:** none

### [ ] 2. Wire the flag in main.go
**File:** main.go
**Context:** [config/config.go](config/config.go)

Reviewers can check the diff against the plan, spot scope creep, and see exactly which files the model was given. Because each step touches one file, the history comes out as small, readable commits.

How the plan reaches the review is up to you. Commit it, paste it into the pull request description, link to it, or keep it local. YACT does not prescribe a way, so whoever leads the team can pick what fits.

Honest trade-offs

  • You choose the context. YACT will not go looking for files, so you need to know your codebase.
  • It rewrites whole files. Keep them to a few hundred lines, because every edited file has to fit in the model's output limit.
  • It never runs your tests or retries. You do that.
  • It works with Anthropic's API only, for now.

A good fit

You know your codebase, you want edits you can predict and script, and you keep files small.

Not a fit

You want a tool that finds the files itself, runs the tests and fixes what broke.

Privacy and safety

  • Your API key is stored on your machine in ~/.yact/config and sent only to Anthropic's API.
  • There is no telemetry. The only network calls are the API calls you trigger, and the system-prompt downloads you ask for with -d.
  • You choose what is sent: the files your task mentions, the message files in .yact/, and the task itself. --verbose lists every path.
  • YACT writes the files the model returns. Run it in a version-controlled working tree and read the result with git diff, or use -n to read a response first and y commit to apply it.

Questions

Does it send my whole repository?

No. Only files whose paths appear in your task are sent, together with the message files in .yact/.

Which models can I use?

Anthropic's Claude models: Haiku (the default), Sonnet, Opus and Fable. Pick one with -c 1 to -c 4 or set it with y config claude_model. Availability depends on your Anthropic account.

What does it cost?

You use your own Anthropic API key and pay Anthropic for what you use. YACT prints the token counts and an estimated cost after every call.

How is it different from aider, Claude Code or Cursor?

Those tools are interactive and agentic: they explore, loop and often run commands. YACT is one-shot and stateless, and it does only what you ask.

Is it made by Anthropic?

No. YACT is an independent open-source project. It is not made, endorsed or supported by Anthropic PBC.

Make it yours

Add a command without touching the code

Every text file in ~/.yact/systemprompts/ becomes a command. Drop in review.txt and you have y review. Write an explain.txt that explains instead of editing and you have a command for onboarding. A flags: line at the top picks the model and turns writing off. No rebuild, no plugin API, no configuration language: a prompt is a file you can read and share.

cat > ~/.yact/systemprompts/explain.txt <<'EOF'
flags: c2n
You are a patient mentor. Explain the code you are given in plain
language: what it does, why it is written that way, and what to read next.
Do not write or change any code.
EOF

y read "commands/*.go"
y explain "how is a command dispatched?"

A codebase you can read in an afternoon

YACT is a few thousand lines of Go, split into small packages (api, commands, config, index and logic) with one clear job per file. If you want a new feature, a new language for the code index, or a bug fixed, it is approachable.
