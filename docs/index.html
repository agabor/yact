Lint the prompt.
Review the change against its plan.

YACT is a command-line tool for AI-assisted coding that works one way: plan first. You write a prompt. The model turns it into a plan and lists what your prompt left unclear. One model call then implements each step. You put the plan in the pull request, so the reviewer can see what was asked.

@@ 01 · The problem @@

AI writes the code faster. The cost shows up later.

Most coding tools take a short prompt, decide everything else themselves and return a change. That is fast, but it has five costs:

The model changes more than you asked

The prompt did not say which files to change, so the model chose.

The model fills gaps without telling you

Where the prompt was vague, the model picked an answer and kept going. You find out in review, or after the merge.

Review takes longer

A pull or merge request shows the diff but not the intent. The reviewer has to work out what was asked, what the model assumed and which code the model was shown.

Developers lose touch with their code

When a tool explores the code and decides for you, you stop building your own picture of the codebase.

Juniors learn less

Much of what juniors learn from seniors, they learn in review. A pull request that nobody can review properly teaches nothing.

A better model reduces these costs but does not remove their cause: nobody checked the prompt, and nobody wrote down the intent.

@@ 02 · The principle @@

A prompt is a program in a very high-level language.

A program can be checked before it runs, and so can a prompt. When you run y plan, the model checks your prompt for two properties and writes the results into the plan. At that point no code has been written. This check is the lint.

1

Complete

Everything the prompt refers to must be something the model can see. If the model needs code it was not given, it does not guess: it lists the files under ## Missing context. This is an error. act refuses to run until the section is gone.

2

No silent assumptions

Where the prompt leaves a decision open, the model writes down the decision it made under ## Assumptions. This is a warning, so act still runs. Read each entry. If you agree with it, leave it in the plan. If you disagree, state what you want in the prompt and run y plan again.

A plan is ready when it has no Missing context section and you agree with every assumption.

The lint is not a proof. The model does the checking and can overlook something, so a plan without an Assumptions section may still contain an assumption. A stronger model overlooks less, and -m lets you plan with one. You still read the plan and check the change.

Read The YACT way

y plan, after linking the missing file # Goal ## Steps ### [ ] 1. Add email validation ## Assumptions - Invalid addresses return an error. (no ## Missing context) Ready: y -s next act
@@ 03 · The plan @@

The plan ties each change to its intent and its context.

A plan is a Markdown file. You read it, and edit it if you want to, before act writes any code. It records four things in one place.

01

The intent

The goal in your words, followed by the steps that reach it.

02

The change

Each step names the one file it changes, so you see the scope before any code is written.

03

The context

Each step links the files the model receives when it implements that step.

04

The assumptions

The decisions the model made where your prompt left them open.

This is what helps a reviewer. With the plan next to the pull request, the reviewer compares the change with what was asked.

YACT keeps the plan in yact-prompt.md and does not attach it for you. y new deletes that file, so commit the plan or copy it into the pull request before you start the next change. Your team decides which of the two.

@@ 04 · How it works @@

From prompt to pull request in five steps.

  1. Write the prompt and link the files

    y new starts an empty prompt. y read links files by path or glob. y keyword Signup links every file that contains the word, and ((Signup)) in the prompt runs the same search each time you run a command. The linked files are the context: they are the only code the model sees.

  2. Plan, then read the two sections

    y plan turns the prompt into a plan with one file per step. Link the files that ## Missing context lists and check each entry under ## Assumptions. If you changed anything, run y plan again.

  3. Implement one step

    y -s next act implements the next unticked step: it writes the complete file and ticks the step. If act finds a problem in the plan, it writes a feedback note, and YACT prints it.

  4. Check the change

    Compare git diff with the step and run your tests. Then implement the next step.

  5. Open the pull request

    Include the plan, so the reviewer has the intent, the files and the assumptions.

terminal $ y new $ y read "internal/signup/*.go" $ y plan "validate email addresses on signup" $ y -s next act $ git diff
yact-prompt.md, after step 1 # Goal Validate email addresses on signup. ## Steps ### [x] 1. Add email validation **File:** internal/signup/validate.go **Context:** internal/signup/signup.go ### [ ] 2. Cover it with tests **File:** internal/signup/validate_test.go **Context:** internal/signup/validate.go

By default, plan and act also send an index: a list of the names of the files, classes and functions in your project, without their code. With the index, the model can name code it was not given and ask for it. The index covers Go, PHP, JavaScript, C#, Swift and Kotlin, and -i none turns it off.

After every call, YACT prints the model, the token counts and the estimated cost. Add --dry-run --verbose to see exactly what a command would send, without calling the API.

@@ 05 · Context by keyword @@

Know the name but not the files? Link by keyword.

A path works when you know where the code is. For a rename, or for a change to something used in many places, give YACT the name and it links every file that contains it.

y keyword PlanStep

Searches once and writes a link to every matching file into yact-prompt.md. The list is a snapshot that you can read and shorten.

((PlanStep))

Write it in the prompt. The search runs each time you run a command, so files created later are included. YACT removes the marker before it sends the text.

Whole words, any naming style

plan step matches PlanStep and plan_step. Only files with known extensions are searched, and y config ext vue adds one. --dry-run --verbose shows which files matched.

A trivial change does not need a plan. For a rename, for example, give the prompt directly to act. Keywords work there too:

y act "Rename PlanStep to Step and update every use. ((PlanStep))"

A keyword links files by their content. With --dry-run --verbose you can see the list before anything is sent.

@@ 06 · Code principles @@

YACT also has rules for the code it writes.

The lint checks your prompt. Sixteen code principles guide the code. plan, act, review and analyze all include the same list, and the list has one goal: every piece of code can be understood from what is visible in one place.

Why YACT needs them

Each call sees only the files you linked, and act writes every changed file back in full. Code that can be understood from one place needs few linked files, and a small file is quick to rewrite.

What they ask for

Searchable names, one job per function, no hidden side effects, logic kept apart from I/O, precise types, tests, and source files under about 200 lines.

Where they apply

Only in code that a step writes or changes. act does not refactor code that the prompt did not mention, and where the plan and a principle disagree, the plan wins.

The principles are one text file, so you can change them to match your team's rules. Read the code principles

@@ 07 · Compared @@

Not a smaller agent. A tool with a method.

Most agents and IDE assistants can plan first if you ask them to. In YACT, planning first is the default, and the whole tool is built around it.

If you want a tool that finds the files, runs the tests and fixes the failures, use an agent. If you want every change to start from a linted prompt and reach the reviewer with its plan, use YACT. Many people will use both.

@@ 08 · Who it is for @@

For developers, and for the people who review their work.

Developers who know their code

You decide what changes, and the model does the typing. Because you write the prompt, link the files and read the plan, you stay familiar with your code.

Team leads

You decide how your team works with AI. With YACT, every AI-assisted pull request can include the plan it was made from.

Teams where review is the bottleneck

Comparing a change with its plan takes less effort than working out the intent from a diff, and the model's assumptions are already listed.

Seniors who mentor juniors

When a junior's pull request includes its plan, you can review the junior's thinking as well as the code. That review is where the junior learns.

@@ 09 · Trade-offs @@

What the method costs you.

Each of these costs is a deliberate choice.

−You link the files. YACT does not explore the code for you, so you need to know roughly where a change belongs. Keywords find files by name, ask answers questions about the code you link, and the plan lists what is still missing.
−You read the plan. You have to supply the missing context and check every assumption. That is work. If you skip it, the same work comes back in review.
−Files must be small. act writes every file it changes back in full. A long file makes the call slow and expensive, and gives the model more room for edits you did not ask for. Keep files under about 200 lines. YACT warns above 300.
−Legacy code is hard. YACT is easy to introduce on a new project or a clean codebase. On a legacy codebase with very large files it is hard: every step rewrites a long file and needs a lot of context, and YACT does not refactor code that the prompt did not mention.
−You run the tests. YACT never runs anything and never retries. If a test fails, pipe the output to y output and write the next prompt.
−Anthropic models only, for now.
+A good fit. You know your codebase, its files are small, and you want every change to start from a plan you have read.
−Not a fit. You want a tool that finds the files, runs the tests and fixes the failures by itself, or most of your code is in very large files.
@@ 10 · Make it yours @@

Every command is a text file.

Six commands come with YACT. Each one is a plain-text system prompt in ~/.yact/systemprompts/. Add a file there and you have a new command, with nothing to rebuild. The lint rules and the code principles are in these files too, so you can read them and change them.

plan
Turns a prompt into a plan with one file per step, and lists the missing context and the assumptions
act
Implements steps by writing complete files, following the plan and the code principles
ask
Answers questions about the linked code and changes nothing
review
Asks the model to review a diff against its prompt
analyze
Checks code against the code principles
bash
Prints shell commands for you to read and run yourself

Before you change a prompt that came with YACT, copy it to a new name. -d downloads the original again and overwrites your edits.

~/.yact/systemprompts/ask.txt, the first lines flags: --model sonnet --output print CODEBASE QUESTION ANSWERING ASSISTANT You are a codebase expert assistant. Your job is to: - Answer questions about how the codebase works - Explain code functionality and architecture $ y ask "how does keyword search pick files?"
@@ 11 · Questions @@

Common questions.

What if the plan lists assumptions?

Read each one. An assumption is a decision the model made because the prompt left it open. If you agree, leave it in the plan. If you disagree, state what you want in the prompt and run y plan again. Assumptions never block act.

Does the lint prove the code is right?

No. The model does the lint during the plan call, and the two sections show only what the model noticed. It can overlook something, so you still read the plan, check the change and run your tests. What the lint gives you is the open decisions before any code is written, when changing one costs a sentence.

Does it send my whole repository?

No. It sends the prompt, the files linked in the prompt or the plan, and two optional inputs if you use them: .yact/domain.txt and output captured with y output. By default, plan and act add an index of file, class and function names, without code; -i none turns it off. A keyword can match many files, and --dry-run --verbose shows what would be sent.

Do I always need a plan?

No. For a trivial change, such as a rename, give the prompt directly to act. For any change that a reviewer will need to understand, plan first.

Can I use it on an existing codebase?

Yes, if its files are small and its structure is clear. On a legacy codebase with very large files it is hard, because act rewrites every changed file in full. It is easiest on a new project.

Does it change my coding style?

plan and act follow sixteen code principles, but only in code that a step writes or changes, and they are told to match the conventions already in the file. The principles are one text file that you can edit.

Which models can I use?

Each command has its own default: plan, act and bash use Claude Haiku, and ask, review and analyze use Sonnet. -m selects Haiku, Sonnet, Opus or Fable for one call, if your Anthropic account has access to it.

What does it cost?

YACT is free. You pay Anthropic directly for the tokens you use, and YACT prints the token counts and the estimated cost after every call.

Where do my API key and code go?

The key is stored in ~/.yact/config and sent only to Anthropic. The files you link are sent to Anthropic's API and nowhere else. There is no telemetry. Apart from the API calls, YACT contacts only GitHub, to download system prompts and skills from the project's repository.

Can it write outside my project?

No. YACT rejects absolute paths and paths that leave the project directory. Inside the project, the model can write or delete any file, not only the linked ones. Check the change with git diff before you commit.

How is it different from aider, Claude Code or Cursor?

Those tools let you work in any way you like, and most can plan first if you ask. In YACT, planning first is the default: the prompt is linted, you read the plan before any code is written, and the plan goes to the reviewer with the change. YACT also does less. It makes one call per command, and it never explores, runs tests or retries.

Is it made by Anthropic?

No. It is an independent open-source project under the GNU GPL v3.
