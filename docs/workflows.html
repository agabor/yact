What they do

YACT keeps all its state in files and makes one API call per command, so a workflow can run it the same way you would at a terminal. The YACT repository is developed with four such workflows. Each one starts when someone adds an action label to an issue or pull request.

LabelOnResult
implementan issueA plan, the code and a new pull request with the plan as its description
updatea pull requestThe plan updated from the latest comment, and new commits on the branch
fixa pull requestCommits that fix a failing build, failing tests or go vet findings
reviewa pull requestA review posted as a comment

A second, optional label picks the model: haiku, sonnet or opus.

  • Without a model label, implement, update and fix use Haiku and review uses Sonnet. If an issue or pull request has more than one model label, the strongest wins.
  • The model label stays where you put it, so a single sonnet label on a pull request applies to every later run on it.
  • The workflow reads the labels when it starts, so add the model label first.
  • The action label is removed when the run ends, whether it succeeded or not. Add it again to run the workflow again.

See them at work: pull request #24 was planned and implemented from an issue by yact-issue.yml. Pull request #22 was too, and then got a second commit from yact-update.yml after a comment. Every branch named yact/issue-… in the repository's history came from the same workflow.

Set up

  1. Copy the workflows. Take the ones you want from .github/workflows in the YACT repository and put them in the same folder of yours: yact-issue.yml, yact-update.yml, yact-fix.yml and yact-review.yml. Each one downloads the latest YACT release binary when it runs.

  2. Add your API key as a secret. The workflows read it from ANTHROPIC_API_KEY and store it with y config on the runner.

    gh secret set ANTHROPIC_API_KEY

  3. Create the labels.

    Four action labels and three model labels:

    for label in implement update fix review haiku sonnet opus; do
  gh label create "$label"
done

  4. Let workflows open pull requests. In your repository settings, under Actions, General, Workflow permissions, turn on Allow GitHub Actions to create and approve pull requests. yact-issue.yml needs it to open the pull request. It is off by default for repositories in a personal account; repositories in an organization take the organization's setting, which an owner may have to change first.

  5. Adapt the build steps to your language. The workflows are written for Go: they set up Go, run go fmt before committing, and yact-fix.yml runs go build, go test and go vet. Replace these with your own formatter, build and test commands. The YACT steps stay the same.

The runner needs to reach github.com for the binary and raw.githubusercontent.com for the system prompts, which are downloaded from the main branch of the YACT repository on every run.

Issue to pull request

yact-issue.yml runs when an issue gets the implement label.

  1. Write the task. The issue title and body become yact-prompt.md.

  2. Plan. y plan turns the issue into a plan. If the plan has a ## Missing context section, it runs once more with those files; if the section is still there, the run stops instead of guessing.

  3. Implement. On a new branch, yact/issue-<number>, y act implements every step. If the response cannot be applied, the raw response is uploaded as a run artifact so you can see why.

  4. Commit. After formatting, the staged diff is sent to y query, which writes the commit message. If that call fails, the issue title is used.

  5. Open the pull request. Its description is the plan followed by Closes #<number>, so the reviewer sees what was meant to change, and the later workflows can read it back.

The heart of it is five commands:

y new
gh issue view "$ISSUE_NUMBER" --json title,body \
  --jq '.title + "\n\n" + (.body // "")' > yact-prompt.md
y -m "$MODEL" --no-progress plan
git checkout -b "yact/issue-$ISSUE_NUMBER"
y -m "$MODEL" --no-progress act

Update a pull request

yact-update.yml runs when a pull request gets the update label. Write what should change as a comment first, then add the label.

The pull request description (the plan) and the latest comment become the prompt. y plan checks which steps are already in the code, keeps the rest and applies the comment. y act implements the new plan, and the result is committed and pushed to the same branch.

Fix a pull request

yact-fix.yml runs when a pull request gets the fix label. It runs the build, the tests and go vet in turn. For each one that fails:

gh pr view "$PR_NUMBER" --json body --jq '.body' > yact-prompt.md
y compact
y output < "$RUNNER_TEMP/test.txt"
y -m "$MODEL" --no-progress act "fix tests"

y compact keeps only the links of the plan, so the files the change touched are sent without the old instructions. y output adds the error log. The fixes are committed and pushed to the branch.

Review a pull request

yact-review.yml runs when a pull request gets the review label. It needs no write access to the code.

The review gets everything a human reviewer would want: the plan from the description, the issues the pull request closes (or its title, if it closes none), the diff through y output, and the current content of every changed file through y read. y review checks correctness first, then security, then the code principles, and the response is posted as a comment.

gh pr diff "$PR_NUMBER" > "$RUNNER_TEMP/pr.diff"
y output < "$RUNNER_TEMP/pr.diff"
y -m "$MODEL" --no-progress review "$(cat "$RUNNER_TEMP/request.txt")"
gh pr comment "$PR_NUMBER" --body-file .yact/temp/buffer.txt

Safety and cost

  • Only people who can label can trigger a run. Adding a label needs triage access or more, so someone who only opens an issue cannot spend your API credit. Only the action labels start a run; a model label on its own does nothing.
  • Read the issue before you label it. Its text becomes the prompt. Whatever the model writes lands on a branch and in a pull request; nothing is merged without you.
  • Untrusted text stays in files. Issue and pull request text reaches YACT through files and quoted variables, never through workflow expressions in shell commands.
  • Costs are small and visible. An issue run makes three or four calls: one or two to plan, one to implement and one for the commit message. Each call prints its token counts and estimated cost in the run log. The Haiku default costs the least.
  • Checks on a workflow's pull request wait for approval. When a pull request is opened or pushed to with the default GITHUB_TOKEN, GitHub creates the runs of your other workflows in an approval-required state, and someone with write access has to approve them. Use a token from a GitHub App or a personal access token if you want them to start straight away. See Triggering a workflow.

Write your own

Any sequence of YACT commands makes a workflow. A few things help in CI:

--no-progress
Turns off the spinner, which only adds noise to a log.
-m "$MODEL"
Picks the model explicitly: haiku, sonnet, opus or fable. The workflows set MODEL in a first step from the labels on the issue or pull request.
buffer.txt
.yact/temp/buffer.txt holds the last response, also for ask, review and query calls. Post this file rather than capturing standard output.
--dry-run --verbose
Prints the files and the prompt a step would send and skips the call, so you can debug a workflow without spending tokens.
y config
Store the key with y config anthropic_api_key on the runner: YACT does not read the ANTHROPIC_API_KEY environment variable by itself.

YACT can also write the workflow for you. The workflow skill teaches the model how YACT behaves in CI:

y read .github/workflows/yact-review.yml
y --skill workflow act "add a workflow that runs y analyze on pull requests labelled analyze"
