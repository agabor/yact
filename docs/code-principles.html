Code principles

YACT has sixteen principles for the code it plans, writes and reviews. They have one goal: every piece of code can be understood from what is visible in one place, and mistakes are caught by types, the compiler and tests rather than by careful reading.

Why YACT has them

The YACT way is about the prompt. These principles are about the code. YACT needs both, for two reasons.

  • Each call sees only the files you linked. Code that can be understood from one place needs few linked files. Code with hidden side effects, generic names or implicit wiring needs many, and the model is more likely to miss one.
  • act writes every changed file back in full. A small file is quick and cheap to rewrite, and its diff is easy to check.

The principles also keep the code readable for people. A person who reviews a change has the same limit as the model: they can only judge what they can see.

The text below follows the file that the model receives, lightly edited for reading. The file in the repository, systemprompts/include/principles.txt, is the authoritative version.

The sixteen principles

P1. Searchable names
Names reveal intent and are unique enough to find with a text search. No generic names (data, info, utils, helpers, manager, process, handle). No identifiers built from strings at runtime. One name per concept.
P2. Single responsibility
Each function, type and module has one job and one reason to change.
P3. No hidden side effects
A function does what its name and signature say, and nothing else. It does not mutate arguments, globals or shared objects unless that is its stated purpose.
P4. Command-query separation
A function either returns information or changes state, not both. Returning an error together with a result is fine.
P5. Functional core, imperative shell
Business logic lives in pure functions. File system, network, database, clock, randomness, environment and console output live in a thin outer layer that calls the core.
P6. Illegal states unrepresentable
Model states with types that cannot hold invalid combinations: sum types, enums, sealed classes, separate structs, or the closest construct the language offers. Do not use loose strings, booleans that exclude each other, or optional fields that depend on each other.
P7. Parse, don't validate
Convert untrusted input (user input, CLI arguments, files, network data, LLM output) into precise types once, at the boundary. Inner code takes those types and does not check them again.
P8. Explicit over implicit
Plain calls with visible arguments. No magic decorators, reflection-based wiring, monkey-patching, implicit conversions, hidden global state or behavior that depends on naming conventions.
P9. Static types
Type every function signature and data structure the language allows. No any, interface{}, untyped maps or dicts where a concrete type fits.
P10. Wrapped dependencies
Third-party libraries and external services are called through a thin interface the project owns, not from all over the code.
P11. Deep modules
A module has a small, simple interface that hides substantial work. Avoid shallow pass-through layers.
P12. Shallow structure
Composition over inheritance, early returns over nesting, short call chains and few layers of indirection.
P13. Simple and conventional
Build only what the task needs now. Readable over clever. Use the mainstream idioms of the language and of the codebase.
P14. Comments explain why
Names and types say what the code does. Comments state intent, business rules, invariants, constraints and non-obvious decisions. No comments that restate the code.
P15. Tests
Logic is covered by fast, independent, deterministic tests that run with one command. Pure functions are tested directly, without mocks.
P16. Consistency
Formatting, naming and structure match the surrounding code.

Four defaults

Developers disagree about some trade-offs. For four of them, the principles state a default so that the model does not choose a different answer on every call.

D1. Duplication
Tolerate small duplication until the right abstraction is clear. Do not merge code that only looks alike. Do remove duplication of one business rule.
D2. Function size
Keep related logic together in one readable function rather than scattering it across many tiny ones. Split a function when it has more than one responsibility, not when it reaches a line count.
D3. Organization
Follow the existing layout of the codebase. When a new module is needed, keep the code of one feature together.
D4. File size
Keep source files under about 200 lines and split them before 300, because every change rewrites the whole file. Split along responsibilities inside the same package or module and keep its public interface unchanged, rather than creating new modules or shallow wrappers.

How YACT applies them

Four of the six commands include the principles, so code is planned, written and reviewed by the same rules.

plan
Designs the steps so that the resulting code follows the principles. Where a principle explains a design decision, the step names it, for example "(P7: parse once at the boundary)". plan does not add steps that only refactor, wrap or rename code the goal does not need.
act
Applies the principles to every function and type it writes or changes. It leaves all other code unchanged, even code that breaks a principle. When it extends existing code, it follows the pattern already used there.
review
Reports a violation only when it makes the changed code harder to change or easier to break, and names the principle.
analyze
Checks the files you link against all the principles, or against the ones you name, and reports what it finds. It changes nothing.

The plan has priority. If a plan and a principle disagree, act follows the plan. The principles decide only what the plan leaves open.

The principles shape how a goal is reached. They do not change the goal: YACT does not refactor your code because it breaks a principle. If you want that, ask for it in a prompt.

Changing them

The principles are one text file on your machine:

~/.yact/systemprompts/include/principles.txt

Edit it to match your team's rules. The change applies to plan, act, review and analyze from the next call. Keep the identifiers (P1, D4) stable if you can, because plans and reviews refer to them.

Keep a copy of your version. Running y download prompt for one of those four commands downloads the original file again and overwrites your edits.

Some principles assume a statically typed language (P6, P9). In a dynamically typed codebase, the model applies them as far as the language allows, and you may want to reword them.

New code and legacy code

YACT is easy to introduce where the code already follows these principles, or where there is no code yet. On a new project, plan and act follow the principles from the first file.

It is hard to introduce on a legacy codebase with very large files:

  • Every step rewrites a whole file. For a file of several thousand lines, that is slow and expensive, and the response can reach the output limit.
  • Tangled code needs a lot of context. The plan lists more missing context, and each step links more files.
  • act does not refactor code that the prompt did not mention, so the code does not get cleaner as a side effect of other changes.

YACT warns before a call about every linked file over 300 lines. To see how far a part of your codebase is from the principles, link its files and run y analyze.
