How it works

Every change follows the same loop. The tool enforces part of it; the rest is habit.

  • 1. Prompt
  • 2. Plan
  • 3. Resolve
  • 4. Act
  • 5. Check
  • 6. Hand over
  • Shortcuts
  • Habits

1. Write the prompt and link the files

A change starts with an empty prompt, the files it needs, and a request in plain words.

y new
y read "internal/signup/*.go"
y prompt "validate email addresses on signup"

The linked files are the only code the model sees. That is deliberate: choosing them requires knowing which code a change touches, and keeps the developer in the codebase.

When you know a name but not where it is used, link by keyword: y keyword Signup links every file that contains the word, and ((Signup)) typed into the prompt runs the same search on every call.

2. Plan

y plan

The model turns the prompt into a plan in yact-prompt.md: a goal, then steps that each name the file they change and link the files they need. It also gets an index of the names of files, types and functions in the project, so it can ask for code it was not given.

# Goal

Validate email addresses on signup.

## Steps

### 1. Add email validation

**File:** internal/signup/validate.go
**Context:** internal/signup/signup.go

### 2. Cover it with tests

**File:** internal/signup/validate_test.go
**Context:** internal/signup/validate.go

The default model is Haiku. For a difficult or unfamiliar change, plan with a stronger one (y -m sonnet plan): it notices more of what the prompt left open.

3. Resolve what the plan lists

The plan ends with up to two sections. They show fastest where the prompt was weak, so read them before the steps.

  • Missing context lists files the model needed and did not get. Link them, or simply plan again: the entries are links, so the files are sent next time.
  • Assumptions lists decisions the model made because the prompt did not say. Tick each one you agree with. Where you disagree, write an Answer: line under it and plan again, then read how the model understood you and tick it.
## Assumptions

- [x] **A1. Unclear:** the prompt does not say what happens to an invalid
  address. Taken: signup returns an error.
- [ ] **A2. Unclear:** the prompt does not say where the error is shown.
  Taken: on a new page.
  Answer: inline, after the field loses focus

y act refuses to run while either section has an open entry. The model cannot tick a box: YACT keeps a tick only if a person ticked that entry before and its wording has not changed.

4. Act

y act

One call sends the whole plan with the files it links, and YACT writes back the files in the response. A response may only write files the prompt or plan links; a new file counts if the plan links it.

If the model finds a problem in the plan while writing code, it leaves a note in .yact/temp/feedback.md, which YACT prints. Treat the note as a bug in the prompt.

5. Check the change

git diff

Read the diff against the plan and run the tests; YACT does not run them. If only part of the plan was implemented, y plan drops the finished steps, and y act continues.

If the change is wrong because the prompt left something open, fix the prompt and plan again rather than patching the code, so the plan still describes what was done.

6. Hand it over with its plan

The plan records what was asked, which files changed, which files the model saw and which decisions were accepted. Commit it with the change or paste it into the pull request, so the reviewer reads the change against it.

YACT does not attach it anywhere, and y new deletes it, so do this before the next change.

Shortcuts

  • Trivial changes skip the plan. For a rename or a one-line fix, write the prompt and run y act directly.
y prompt "Rename PlanStep to Step and update every use. ((PlanStep))"
y act
  • Questions change nothing. y ask answers questions about the linked code. y review reviews a diff written to a file and linked.

Habits that help

  • Keep plans small enough for one call and one review. A bigger goal becomes several smaller goals, one after the other.
  • Keep files small. The model writes every changed file back in full, so a 150-line file is quicker, cheaper and easier to check than a 900-line one.
  • Start an unrelated change with y new. y prompt appends, so old text would be sent again.
  • Use --dry-run when unsure what will be sent. It lists every file and makes no call.
