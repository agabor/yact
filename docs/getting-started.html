Getting started

About ten minutes from nothing to a first reviewed change.

What you need

  • A terminal and a Git repository to work in. YACT writes files into your project, so use a working tree where you can review changes and undo them.
  • An Anthropic API key, created in your own account at console.anthropic.com. It is pay-as-you-go, so the account needs some credit. YACT prints an estimated cost after every call.
  • Either the Go toolchain, to build from source, or a prebuilt binary for your platform.

Install

Build from source (recommended)

YACT is written in Go (1.26 or newer), so building from source means you run code you can read.

git clone https://github.com/agabor/yact.git
cd yact
go build -o y .
mkdir -p ~/.local/bin
mv y ~/.local/bin/

Make sure ~/.local/bin is on your PATH. The repository also has an install.sh that builds the binary and installs it to /usr/local/bin with sudo.

Prebuilt binary

Download the file for your platform from the releases page.

PlatformFile
Linux (x86-64)yact-linux-amd64
Linux (ARM64)yact-linux-arm64
macOS (Apple silicon)yact-darwin-arm64
macOS (Intel)yact-darwin-amd64
Windows (x86-64)yact-windows-amd64.exe

On Linux and macOS, make it executable and put it on your PATH under the name y:

chmod +x yact-linux-amd64
mkdir -p ~/.local/bin
mv yact-linux-amd64 ~/.local/bin/y

On Windows, put yact-windows-amd64.exe in a folder on your PATH (renaming it to y.exe is convenient), or run it from where you downloaded it.

Check that it works with y --version. Releases do not include checksum files yet; if you need to verify what you run, build from source.

Configure

Save your key. It is written to ~/.yact/config on your machine and used only for calls to Anthropic's API.

y config anthropic_api_key <your-own-anthropic-key>
y config

The second command shows your current settings, so you can check that it worked. YACT reads the key only from this file, not from the ANTHROPIC_API_KEY environment variable.

The system prompts download by themselves from the YACT repository the first time you use a command. Every system prompt is a plain text file in ~/.yact/systemprompts/, and every file there becomes a command: plan writes a plan, act writes code, ask answers questions, review reviews a diff, analyze checks code against the code principles and bash writes shell commands. Read them whenever you like. To fetch the latest version of one, add -d:

y -d act

Finally, keep YACT's working files out of your commits. In the repository you work on, add this to .gitignore:

.yact/temp
.yact/batch_job_id.txt

The other files in .yact/ are settings worth sharing with your team: the file extensions to search, the folders to skip and an optional domain.txt that describes your project to the model in every call.

The task and the plan live in yact-prompt.md. Whether it is committed or attached to a pull request is up to you; add it to .gitignore too if your team does not want plans in the repository.

Make your first change

This walk-through uses a plan, so you read what will change before any code is written. Run it inside a Git repository.

  1. Start clean. This removes any earlier task file, captured output and code index.

    y new

  2. Pick the files the task needs. Quote glob patterns so your shell does not expand them first. Each file is added to yact-prompt.md as a link. To add every file that contains a word instead, use y keyword Transaction.

    y read main.go
y read "commands/*.go"

  3. Ask for a plan. The response is saved to yact-prompt.md instead of your source files. Open it, read it and edit anything you disagree with. Each step changes one file and ends with a Context line that links the files that step needs.

    y plan "add a --version flag"

    If the plan ends with a ## Missing context section, the planner had to guess what is in those files. Run y plan once more: the files listed there are sent this time, and the plan is revised. YACT will not implement a plan that still has that section.

  4. Implement the first step. YACT sends the goal and that one step, makes one API call, writes the files and ticks the step off in the plan.

    y -s next act

  5. Review the change. Read the diff as you would read a colleague's. If it is wrong, fix the plan or the code and try again.

    git diff

  6. Repeat. Run steps 4 and 5 until every step heading reads [x]. To run all remaining steps in one call instead, use y act without -s. Once every step is done, YACT stops with no steps remain; untick a step to run it again, or start the next task with y new.

A quicker path for small changes

You can skip the plan and give the task directly. The files you added with y read are sent as context.

y read main.go
y act "add a --version flag"

The task you type is also added to yact-prompt.md, so the next call sees it too. Run y new before an unrelated task.

Check a request before you send it

With --dry --verbose, YACT prints every file and the full prompt it would send, and stops before the API call. It costs nothing.

y --dry --verbose act "add a --version flag"

act only writes a response that is pure code. If the model added a sentence of explanation, nothing is written; the response is kept in .yact/temp/buffer.txt, and after reading it you can apply it anyway with y commit.

Choose a model

act uses Haiku by default. Add -c 2 for Sonnet, -c 3 for Opus or -c 4 for Fable. Which models you can use depends on your Anthropic account.

Ask without changing anything

The ask command answers questions about the files you pick and never writes to your source files. It is a good way to understand a codebase before you change it.

y new
y read commands/call.go
y ask "why does this function return early?"

For a bigger picture, add a code index with -i. It lists the declarations in your project, without the code inside them. Level 1 lists public declarations and level 2 lists all of them. It works for Go, PHP, JavaScript, C#, Swift and Kotlin. act and plan include an index by default.

y -i 1 ask "where is the config loaded?"

To check a change before you merge it, send the diff and ask for a review:

git diff main | y output
y review "add a --version flag"

See what is sent and what it costs

A file is sent only when yact-prompt.md links it. Mentioning a path in passing sends nothing. There are three ways to link files:

[main.go](main.go)
A Markdown link sends that one file. This is what y read writes.
[[commands/*.go]]
Double brackets send every file that matches the pattern.
((plan step))
Double parentheses send every file that contains those words, in any casing: PlanStep, plan_step or plan step. This is what y keyword does, at the time of the call.

y read puts its links below a line of dashes. Everything below that line selects files but is not sent as text, so your instructions stay readable.

Hidden folders (except .github), vendor and node_modules are never sent. Add more folders to skip with y config ignore <folder>. Output you capture with y output is sent with every call until you run y new.

To see exactly what goes out, add --verbose. Add --dry as well to stop before the call:

y --dry --verbose ask "how does the parser work?"

YACT warns before the call about any linked file over 300 lines, because the model has to write such a file back in full. After the call it prints the model, the duration, the token counts and an estimated cost.

Use it with a team

Plans in reviews. A plan shows what a change was meant to do, step by step. Commit it, paste it into the pull request description, link to it or keep it local. YACT does not prescribe a way, so the person leading the team decides.

Mentoring. If you are learning, write down what you expect each step of a plan to change before you run it, then compare with the diff. If you are mentoring, ask for the plan first and review it before any code exists.

Shared commands. A command is a text file in ~/.yact/systemprompts/, so a team can share a tuned act.txt or its own explain.txt like any other file. See how.

Automation. The same commands run in CI. Label an issue and a workflow plans it, implements it and opens a pull request; label a pull request and it gets a review. Set up the GitHub workflows.

When something goes wrong

Claude API key not configured
Set your key with y config anthropic_api_key <your-own-anthropic-key>.
no system prompt found for command
The prompt could not be downloaded. Check the command name and your connection, or create the file in ~/.yact/systemprompts/.
response contains free text outside code blocks
This comes from -v, which act turns on by default. Nothing was written to disk. Run the command again, or read the response in .yact/temp/buffer.txt and apply it with y commit.
--no-write and --validate-code cannot be combined
A command's prompt file can turn flags on: act uses -v, plan uses -p and ask uses -n, and these three exclude each other. To see what act would get, use --dry --verbose instead of -n.
Files needed as context are missing
The plan has a ## Missing context section. Run y plan once more.
no steps remain
Every step of the plan is ticked. Untick a step to run it again, extend the plan with y plan "…", or start over with y new.
A file was not sent
Only links send files. Run with --dry --verbose, and check that the path is relative to the project root and not in a hidden or skipped folder.
