Getting started

About ten minutes from an empty terminal to a first change made from a plan.

What you need

  • A terminal and a Git repository to work in. YACT writes files into your project, so work in a repository where git diff shows you every change and you can undo it.
  • Code in small files. YACT rewrites every file it changes in full and warns above 300 lines. On a legacy codebase with very large files it is hard to use; see New code and legacy code.
  • An Anthropic API key, created in your own account at console.anthropic.com. It is pay-as-you-go, so the account needs some credit. YACT prints an estimated cost after every call.
  • Either the Go toolchain, to build from source, or a prebuilt binary for your platform.

Install

Build from source (recommended)

YACT is written in Go (1.26 or newer), so building from source means you run code you can read.

git clone https://github.com/agabor/yact.git
cd yact
go build -o y .
mkdir -p ~/.local/bin
mv y ~/.local/bin/

Make sure ~/.local/bin is on your PATH. The repository also has an install.sh that builds the binary and installs it to /usr/local/bin with sudo.

Prebuilt binary

Download the file for your platform from the releases page.

PlatformFile
Linux (x86-64)yact-linux-amd64
Linux (ARM64)yact-linux-arm64
macOS (Apple silicon)yact-darwin-arm64
macOS (Intel)yact-darwin-amd64
Windows (x86-64)yact-windows-amd64.exe

On Linux and macOS, make it executable and put it on your PATH under the name y:

chmod +x yact-linux-amd64
mkdir -p ~/.local/bin
mv yact-linux-amd64 ~/.local/bin/y

On Windows, put yact-windows-amd64.exe in a folder on your PATH (renaming it to y.exe is convenient), or run it from where you downloaded it.

Check that it works with y --version. Releases do not include checksum files yet; if you need to verify what you run, build from source.

Configure

Save your key. It is written to ~/.yact/config on your machine and used only for calls to Anthropic's API.

y config anthropic_api_key <your-own-anthropic-key>
y config

The second command shows your current settings, so you can check that it worked. YACT reads the key only from this file, not from the ANTHROPIC_API_KEY environment variable.

YACT downloads the system prompt of a command from the YACT repository the first time you use that command. Every system prompt is a plain text file in ~/.yact/systemprompts/, and every file there is a command: plan writes a plan, act writes code, ask answers questions, review reviews a diff, analyze checks code against the code principles and bash writes shell commands. You can read these files at any time. To replace your copy of one with the latest version, add -d. This overwrites any edits you made to that file.

y -d act

Finally, keep YACT's working files out of your commits. In the repository you work on, add this to .gitignore:

.yact/temp
.yact/batch_job_id.txt

The other files in .yact/ are settings worth sharing with your team: the file extensions to search, the folders to skip and an optional domain.txt that describes your project to the model in every call.

The prompt and the plan are in yact-prompt.md, and y new deletes that file. Decide with your team how a plan reaches the reviewer: commit the file with the change, or copy the plan into the pull request. If your team does not want plans in the repository, add yact-prompt.md to .gitignore too.

Make your first change

This walk-through makes a change from a plan, so you read what will change before any code is written. Run it inside a Git repository.

  1. Start clean. This deletes the earlier prompt file, captured output and index, if there are any.

    y new

  2. Link the files the change needs. Quote glob patterns so your shell does not expand them first. Each file is added to yact-prompt.md as a link. To link every file that contains a word instead, use y keyword Transaction.

    y read main.go
y read "commands/*.go"

  3. Ask for a plan. YACT writes the plan to yact-prompt.md and does not touch your source files. Open the plan, read it and edit anything you disagree with. Each step names the file it changes and ends with a Context line, which links the files the model receives for that step.

    y plan "add a --version flag"

    A plan can end with two sections. Together they are the lint of your prompt.

    ## Missing context lists code that the model needed and was not given. The model does not guess; it asks. This is an error: act refuses to run while the plan has this section. Run y plan once more, and the listed files are sent this time.

    ## Assumptions lists the decisions the model made where the prompt left them open. This is a warning and never blocks act, but check each entry. If you agree with it, leave it in the plan. If you disagree, state what you want in the prompt and run y plan again.

    The plan is ready when it has no Missing context section and you agree with every assumption. Why this matters.

  4. Implement the first step. YACT sends the goal and that one step, makes one API call, writes the files and ticks the step off in the plan.

    y -s next act

  5. Check the change. Compare the diff with the step it implements, and run your tests. If the change is wrong, correct the plan or the code and try again.

    git diff

  6. Repeat. Repeat steps 4 and 5 until every step heading reads [x]. To implement all remaining steps in one call instead, use y act without -s. When every step is ticked, act stops with no steps remain. Untick a step to implement it again, or start the next change with y new.

  7. Open the pull or merge request. The plan shows the reviewer what was asked, which file each step changed, which files the model received and what it assumed. Commit the plan or copy it into the request, as your team prefers, before you run y new.

If act finds a problem in the plan or the context, it writes a note to .yact/temp/feedback.md. YACT prints the note after the call. Read it before you check the change.

Without a plan, for trivial changes

A trivial change, such as a rename or a one-line fix, does not need a plan. Give the prompt directly to act. The files you linked with y read are the context.

y read main.go
y act "add a --version flag"

YACT also adds the prompt you type to yact-prompt.md, so the next call receives it too. Run y new before you start an unrelated change.

Check a request before you send it

With --dry-run --verbose, YACT prints every file and the full prompt it would send, and stops before the API call. It costs nothing.

y --dry-run --verbose act "add a --version flag"

act writes files only when the response contains nothing but code. If the model added even one sentence of explanation, YACT writes no files and keeps the response in .yact/temp/buffer.txt. Read it there, and apply it with y commit if it is what you want.

Choose a model

plan and act use Haiku by default. Add -m sonnet, -m opus or -m fable to use another model for one call. Which models you can use depends on your Anthropic account. The lint depends on the model, so a stronger model for y plan is worth trying on a difficult change.

Each command sets its default model in the first line of its prompt file. y config claude_model <name> sets the model for commands whose prompt file names none.

Link files by keyword

Linking files by path works when you know where the code is. When you know only what something is called, link files by keyword. There are two ways to do it, and they differ in when the search runs.

y keyword PlanStep
Searches the project once and adds a link to every file that contains the word. The links are a snapshot: files created later are not included until you run it again.
((PlanStep)) in your prompt
Searches each time you run a command. YACT removes the marker before it sends your text, so the model reads a normal sentence.
y act "Rename PlanStep to Step and update every use. ((PlanStep))"

A keyword matches whole words, in any casing or separator style, so plan step finds PlanStep and plan_step. Only files with the extensions in your settings are searched; add one with y config ext vue. YACT reads markers only in your own prompt, not in system prompts. To see which files a keyword linked, add --dry-run --verbose.

A keyword links files by their content. It helps most with the changes whose files are hardest to list by hand: renames, and changes to something that is used in many places.

Ask without changing anything

The ask command answers questions about the files you link and never writes to your source files. Use it to learn how unfamiliar code works before you change it.

y new
y read commands/call.go
y ask "why does this function return early?"

To ask about more than the linked files, add an index with -i. It lists the files, classes and functions in your project by name, without the code inside them, so the model can find its way around code you did not link. -i public lists public declarations and -i all lists all of them; -i none turns it off. It works for Go, PHP, JavaScript, C#, Swift and Kotlin. act and plan include an index by default.

y -i public ask "where is the config loaded?"

To have the model review a change before you open the pull request, send it the diff:

git diff main | y output
y review "add a --version flag"

See what is sent and what it costs

A file is sent only when yact-prompt.md links it, in your prompt or in the plan. A path that is only mentioned in the text sends nothing. There are three ways to link files:

[main.go](main.go)
A Markdown link sends that one file. This is what y read writes.
[[commands/*.go]]
Double brackets send every file that matches the pattern.
((plan step))
Double parentheses send every file that contains those words, in any casing: PlanStep, plan_step or plan step. This is what y keyword does, at the time of the call.

y read puts its links below a line of dashes. The links below that line still send their files, but the text below the line is not sent, so your prompt stays readable.

Hidden folders (except .github), vendor and node_modules are never sent. Add more folders to skip with y config ignore <folder>. Output you capture with y output is sent with every call until you run y new.

plan and act also send the index by default: names of files, classes and functions, with no code. Turn it off with -i none.

To see exactly what goes out, add --verbose. Add --dry-run as well to stop before the call:

y --dry-run --verbose ask "how does the parser work?"

YACT warns before the call about any linked file over 300 lines, because the model has to write such a file back in full. After the call it prints the model, the duration, the token counts and an estimated cost.

Use it with a team

Plans in reviews. A plan shows what a change was meant to do, step by step: the file each step changes, the files the model received and what it assumed. With the plan next to the pull or merge request, the reviewer compares the change with what was asked. YACT does not attach the plan, so your team decides whether to commit it or copy it into the request.

Mentoring. If you are learning, write down what you expect each step of a plan to change before you run it, then compare with the diff. If you are mentoring, ask for the plan with the pull request and review the change against it. That review is where a junior learns.

Shared commands. A command is a text file in ~/.yact/systemprompts/, so a team can share its own commands, such as an explain.txt, like any other file. To tune a command that came with YACT, copy it to a new name first, because -d overwrites the original. See how.

Shared code principles. plan, act, review and analyze follow one list of code principles. It is a text file too, so a team can agree on one version and share it.

When something goes wrong

Claude API key not configured
Set your key with y config anthropic_api_key <your-own-anthropic-key>.
no system prompt found for command
The prompt could not be downloaded. Check the command name and your connection, or create the file in ~/.yact/systemprompts/.
response contains free text outside code blocks
This comes from --strict, which act turns on by default. Nothing was written to disk. Run the command again, or read the response in .yact/temp/buffer.txt and apply it with y commit.
--strict cannot be combined with --output print
The output mode is apply (write files), print (show the response) or plan (write the plan), and --strict only makes sense with apply. A command's prompt file sets its own defaults: act writes files, plan writes the plan and ask prints. To read what act would produce without writing it, use -o print; to see what it would send, use --dry-run --verbose.
--steps cannot be combined with a prompt argument
-s implements steps that are already in the plan, so it takes no prompt text. Put the instruction in the plan, or leave out -s.
Files needed as context are missing
The plan has a ## Missing context section. Run y plan once more, or add the files yourself with y read or y keyword.
no steps remain
Every step of the plan is ticked. Untick a step to run it again, extend the plan with y plan "…", or start over with y new.
A file was not sent
Only links send files. Run with --dry-run --verbose, and check that the path is relative to the project root and not in a hidden or skipped folder.

The README lists more, and you can ask for help by opening an issue.
