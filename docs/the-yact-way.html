The YACT way

A prompt is a program in a very high-level language. This page explains the method that follows from that idea: how to write a prompt that can be checked, and how to hand the result to a reviewer.

The principle

When you ask a model to change code, the prompt is the program. It says what should happen, and the model compiles it into files. A prompt can be wrong in two ways that can be found without running anything.

  • It can refer to something the model cannot see: a type, a caller or a file that was not linked.
  • It can leave a decision open, so that the model makes the decision without telling you.

These give the two properties that YACT checks. A prompt is complete when the model can see everything the prompt refers to. A prompt has no silent assumptions when every decision the model made for you is written down.

The plan is the same prompt in a more explicit form: a goal and a list of steps. The same two properties apply to it.

YACT works like a linter for these two properties. The model checks them during the y plan call and writes the results into the plan. No code has been written at that point, so closing a gap costs one sentence in the prompt and not a round of review.

Complete: an error

If the model needs to know what is inside a file it was not given, it does not guess. It adds a ## Missing context section to the plan and lists the files there. YACT treats this section as an error: act refuses to run while the plan contains it. The section is for facts about code the model has not seen, such as which functions call a function or which fields a type has.

To fix it, give the model the files. The simplest way is to run y plan again: the entries are links, so the listed files are sent this time. You can also link files yourself with y read or y keyword, or write ((keyword)) in the prompt.

No silent assumptions: an error you resolve

Where the prompt does not say what you want, the model decides and lists its decision under ## Assumptions. Each entry is a decision that you did not make, so YACT makes you decide: every entry has a checkbox, and act refuses to run while one is open.

## Assumptions

- [x] **A1. Unclear:** the prompt does not say what happens to an invalid
  address. Taken: signup returns an error.
- [ ] **A2. Unclear:** the prompt does not say where the error is shown.
  Taken: on a new page.
  Answer: inline, after the field loses focus

You resolve an entry in one of two ways.

  • Accept it. If the model decided what you would have decided, tick the box by hand, as in A1.
  • Answer it. If you want something else, write an Answer: line under the entry, as in A2, and run y plan again. The model changes the steps to follow your answer and rewrites the entry with Decided: in place of Taken:. The box is still open. Read how the model understood you, then tick it.

Only you tick a box. The model always writes open boxes, and after each plan call YACT keeps a tick only if you ticked that entry before and its wording has not changed. If the model rewords an entry you accepted, you accept it again.

The two sections hold different kinds of things. Missing context holds facts about code that the model could not see. Assumptions holds decisions about what you want. Both block act, but you resolve them differently. A fact can be looked up, so you link the file. A decision is yours, so you make it.

The plan ties the change to its intent

A plan that has no missing context, and whose assumptions you have resolved, is more than a to-do list. Each step names the one file it changes and links the files the model receives to implement it. The plan therefore records four things in one place:

  • the intent: the goal in your words, followed by the steps that reach it
  • the change: the file each step changes
  • the context: the files the model received for each step
  • the assumptions: the decisions the model made where the prompt left them open, each one accepted or answered by you

This is what helps a reviewer. When a pull or merge request includes its plan, the reviewer compares the change with what was asked and does not have to work out the intent from the diff.

YACT does not attach the plan for you. The plan is in yact-prompt.md, and y new deletes that file. Commit the plan or copy it into the pull request before you start the next change.

The loop

  1. Write the prompt

    Say what you want in plain words, and link the files that you know the change needs.

  2. Plan

    y plan writes the steps. The two sections list what is missing and what the model assumed.

  3. Resolve the two sections

    Link the files that Missing context lists. Tick each assumption you accept, and write an answer under each one you do not. If you linked a file or wrote an answer, plan again.

  4. Act, one step at a time

    When the plan has no Missing context section and every assumption is ticked, run y -s next act. It implements one step per call. Compare each change with its step.

  5. Hand over the change with its plan

    Include the plan in the pull request, so that the reviewer can compare the change with it.

act can still find a problem in the plan while it writes the code. It then writes a note to .yact/temp/feedback.md, and YACT prints the note. Treat the note as a bug report on the prompt: correct the prompt as well as the code.

Code that suits the method

The method makes two demands on the code. Each call sees only the files you linked, so the code must be understandable from a few files. act writes every changed file back in full, so the files must be small.

YACT's sixteen code principles describe code that meets both demands: searchable names, no hidden side effects, logic kept apart from I/O, precise types, and files under about 200 lines. plan and act follow them in the code they write or change.

This is also why YACT is easy to introduce on a new project or a clean codebase, and hard to introduce on a legacy one. Where files are very large and dependencies are tangled, every step needs a lot of context and a long rewrite, and act does not refactor code that the prompt did not mention.

What it does not do

It does not prove that a change is correct. No linter does. What YACT gives you is narrower: it shows gaps in the prompt that would otherwise stay hidden until review.

It does not find every gap. The model does the checking, and the two sections show what the model noticed. It can overlook an entry, so a plan without an Assumptions section may still contain an assumption. You still read the plan, check the change and run the tests.

It does not limit which files act writes. The plan names one file per step, but inside the project the model can write or delete other files. git diff shows you if it did.

It does not make you think. Ticking a box takes one keystroke. YACT makes each decision explicit and records it in the plan, but it cannot tell whether you read the entry.

It does not run unattended. A plan needs a person to accept or answer its assumptions, so YACT has no workflows that plan and implement by themselves.

Habits that follow

Read the two sections before the steps
They show most quickly where the prompt is weak.
Fix the prompt, not only the output
If a change is wrong because the prompt left something open, correct the prompt and plan again. The plan then matches the code, and the reviewer reads the real intent.
Keep files small
act writes each changed file back in full. A small file is quicker and cheaper to rewrite, and its diff is easier to check.
Put the plan in front of reviewers
Commit it or copy it into the pull request, whichever your team prefers. A reviewer should read the assumptions first: they are the decisions the author accepted.
