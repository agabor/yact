The YACT way

A prompt is a program in a very high-level language. YACT is a tool with a method for writing one well, and for handing the result to a reviewer.

The principle

When you ask a model to change code, the prompt is the program: it says what should happen, and the model compiles it into files. Like any program, it can be wrong in two ways that can be looked for without running anything.

  • It can refer to something that is not there: a type, a caller, a file the model has not been shown.
  • It can leave a choice open, so the model fills it in without telling you.

The plan is the same prompt, written out more explicitly: the goal, then the steps. So both are held to the same two properties. A prompt is complete when every reference resolves, and it has no silent assumptions when every default is visible.

YACT works like a linter for these properties. The model checks them during the y plan call and writes what it finds into the plan, before any code exists. Fixing a gap then costs a sentence instead of a review.

Complete: an error

When the model would have to guess what is inside a file it cannot see, it does not guess: the plan gets a ## Missing context section. YACT treats that as an error: it will not implement a plan that still has the section. Facts about code the model has not seen belong here, such as who calls a function or what a type contains.

You fix it by giving the model the files. Link them with y read or y keyword, write ((keyword)) in the prompt, or run y plan again, which sends the files the section lists.

No silent assumptions: a warning

Where the prompt is open about what you want, the model picks an answer and lists it under ## Assumptions. YACT never blocks on this section, because the choice is yours.

Each entry marks a decision you did not make, so check it. If the assumption is what you want, it is fine and can stay in the plan. If it is not, say what you want in the prompt and plan again.

The two sections differ in kind. Missing context holds facts the model could not see. Assumptions holds choices about what you want. Keeping them apart keeps the first one a reliable gate.

The plan binds the change

Once the two sections are dealt with, the plan is more than a to-do list. Each step names the file it changes and links the context the model is given to write it. So the plan records, in one place:

  • the intent: the goal in your words, then the steps that reach it
  • the change: the file each step touches
  • the context: the files the model was given for each step
  • the assumptions: what the model chose where the prompt was open

This is what helps a reviewer. A pull or merge request that comes with its plan can be reviewed against what was asked, and the reviewer does not have to work out the intent from the diff.

The loop

  1. Write the prompt

    Say what you want in plain words, and link the files you know it needs.

  2. Plan

    y plan writes the steps, and the two sections say what is missing and what the model assumed.

  3. Read the two sections

    Link the files that Missing context asks for, and check the assumptions. Plan again if you changed anything.

  4. Act, one step at a time

    The plan is ready when Missing context is gone and the assumptions are true. y -s next act implements one step per call, and you check each change against its step.

  5. Hand over the change with its plan

    In the pull request, the reviewer reads the change against the plan.

If act still finds a problem in the plan, it writes a note to .yact/temp/feedback.md and YACT prints it. Treat it as a bug report on the prompt: fix the prompt, not only the code.

What it does not do

The lint does not prove that the change is correct. No checker does: proving even a short ordinary program right is extremely hard, and nobody expects that of a linter. What YACT gives you is narrower and still useful. It surfaces gaps that would otherwise stay hidden until review.

It is also limited by the model, which makes the checks. The sections show what the model noticed, so an entry can be missed, and a plan without an Assumptions section is not proof that nothing was open. You still read the plan, check the change and run the tests.

One more guard is possible and not built yet: a strict mode that treats assumptions as errors too, the way a linter can be told to fail on any warning. For now, assumptions are yours to check.

Habits that follow

Read the two sections before the steps
They are the shortest way to see where the prompt is weak.
Fix the prompt, not the output
If a change is wrong because something was open, correct the prompt and run again. The plan then says what the code does, and the reviewer reads the right intent.
Keep files small
A complete file is easier to link, to read and to write back whole.
Put the plan in front of reviewers
Commit it or copy it into the pull request, whichever your team prefers. The assumptions are the first things a reviewer should check.
