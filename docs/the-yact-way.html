The YACT way

A prompt is a program in a very high-level language. YACT is a tool that carries a method for writing one well.

The principle

When you ask a model to change code, the prompt is the program: it says what should happen, and the model compiles it into files. Like any program, it can be wrong in two ways that a tool can look for without running anything.

  • It can refer to something that is not there: a type, a caller, a file the model has not been shown.
  • It can leave a choice open, so the model fills it in without telling you.

The plan is the same prompt, written out more explicitly: the goal, then the steps. So YACT uses one word for both and holds both to the same two properties. A prompt is complete when every reference resolves, and it has no silent assumptions when every default is visible.

YACT works like a linter for these properties. It reports them before any code exists, when fixing them costs a sentence instead of a review.

Complete: an error

If the planner has to guess what is inside a file it cannot see, the plan gets a ## Missing context section. YACT treats that as an error: it will not implement a plan that still has the section. Facts about code the model has not seen belong here, such as who calls a function or what a type contains.

You settle it by giving the model the files. Link them with y read, select them by keyword with y keyword or ((keyword)), or run y plan again, which sends the files the section lists.

No silent assumptions: a warning

Where the prompt is open about what you want, the planner picks an answer and lists it under ## Assumptions. YACT never blocks on this section, because the choice is yours. But each entry marks a decision you did not make, and the plan is easier to trust when there are none.

The two lists differ in kind. Missing context holds facts the model could not see. Assumptions holds choices about what you want. Keeping them apart keeps the first one a reliable gate.

You settle an entry by stating the answer in the prompt, or by changing it if the model chose wrong.

The loop

  1. Write the prompt

    Say what you want in plain words, and link the files you know matter.

  2. Plan

    y plan writes the steps and lists what is missing and what it assumed.

  3. Settle the lists

    Sharpen the prompt or link the files, then plan again.

  4. Act, one step at a time

    The prompt is ready when both lists are empty. y -s next act writes one file per call, and you read each diff.

If act still finds a problem in the plan, it writes a note to .yact/temp/feedback.md and YACT prints it. Treat it as a bug report on the prompt: fix the prompt, not only the code.

What it does not do

The lint does not prove that the change is correct. No checker does: proving even a short ordinary program right is extremely hard, and nobody expects that of a linter. What YACT gives you is narrower and still useful. It surfaces gaps that would otherwise stay hidden until review.

It is also limited by the model. The lists show what the model noticed, so an entry can be missed. You still read the plan and the diff, and you still run the tests.

One more guard is possible and not built yet: a strict mode that treats assumptions as errors too, the way a linter can be told to fail on any warning. For now, assumptions are yours to read.

Habits that follow

Read the lists before the steps
They are the shortest way to see where the prompt is weak.
Fix the prompt, not the output
If a diff is wrong because something was open, change the prompt and run again. The fix then applies to the next task as well.
Keep files small
A complete file is easier to link, to read and to write back whole.
Put the plan in front of reviewers
Commit it or paste it into the pull request. The assumptions are the first things a reviewer should check, and the workflows already do this.
